# ToDoPrioritizer — Architecture Plan (Draft v0.1)

Status: **v1.0 — M0–M7 complete.** This document describes the code as built.
Implements: `docs/REQUIREMENTS.md` v0.3

## 1. Overview

The app is a single-page React application with no backend. The code is
split into four layers. Each layer may only use the layers below it.

```
┌──────────────────────────────────────────────┐
│ UI         React components and views        │  src/ui/
├──────────────────────────────────────────────┤
│ State      hooks + TodoService (use cases)   │  src/state/
├──────────────────────────────────────────────┤
│ Domain     types, rules, selectors (pure TS) │  src/domain/
├──────────────────────────────────────────────┤
│ Data       TodoRepository + implementations  │  src/data/
└──────────────────────────────────────────────┘
```

- **Domain** contains plain TypeScript only. It does not use React, Dexie, or
  the browser, and it has no side effects. All business rules live here.
- **Data** knows how todos are stored. Its interface is the only place that
  would change if a backend were added.
- **State** connects the domain rules to the repository and gives components
  reactive data through hooks.
- **UI** shows the data and turns user actions into calls to the State layer.
  UI code never imports `src/data/` directly.

## 3. Domain layer

### 3.1 Types

The rule "`completedAt` is set if and only if the todo is done" is built into
the type, so the compiler rejects any todo that breaks it:

```ts
export type Quadrant = 'Q1' | 'Q2' | 'Q3' | 'Q4';
export type IsoUtc = string; // e.g. "2026-11-20T22:15:00.000Z"

interface TodoBase {
  id: string; // crypto.randomUUID()
  title: string; // 1–200 characters, trimmed
  description: string; // 0–2000 characters, '' if none
  quadrant: Quadrant | null; // null = Unsorted
  createdAt: IsoUtc;
  updatedAt: IsoUtc;
}
export interface ActiveTodo extends TodoBase {
  isCompleted: false;
  completedAt: null;
}
export interface CompletedTodo extends TodoBase {
  isCompleted: true;
  completedAt: IsoUtc;
}
export type Todo = ActiveTodo | CompletedTodo;
```

Timestamps are ISO-8601 UTC strings. They can be sorted as plain text, are
easy to read in DevTools, and are converted to local time only when shown
(`lib/formatDate.ts`, which uses `Intl.DateTimeFormat`).

### 3.2 Rules (`todo.rules.ts`)

These functions are pure: they never change their input and always return a
new todo. The current time and new ids are passed in as arguments, so tests
can control them.

| Function                               | Requirement | Behavior                                                                                                    |
| -------------------------------------- | ----------- | ----------------------------------------------------------------------------------------------------------- |
| `validateTodoInput(input)`             | FR-4        | Returns `Result<ValidInput, ValidationError[]>`. Trims the title and rejects one that is blank or too long. |
| `createTodo(input, now, id)`           | FR-1        | Returns an `ActiveTodo` and sets `createdAt = updatedAt = now`.                                             |
| `editTodo(todo, patch, now)`           | FR-2        | Changes the title, description, and quadrant. Keeps `createdAt`, `completedAt`, and the completion state.   |
| `completeTodo(todo, now)`              | FR-5        | Returns a `CompletedTodo`. Does nothing if the todo is already done.                                        |
| `reopenTodo(todo, now)`                | FR-6        | Returns an `ActiveTodo` with `completedAt = null`.                                                          |
| `assignQuadrant(todo, q \| null, now)` | FR-14       | Sets the quadrant. Null moves the todo to Unsorted.                                                         |

Every change also sets `updatedAt = now`.

### 3.3 Selectors (`selectors.ts`)

- `filterByStatus(todos, 'all' | 'active' | 'completed')` — FR-9
- `sortForList(todos, filter)` — FR-10. Newest `createdAt` first. The
  Completed filter sorts by `completedAt`, newest first.
- `groupByQuadrant(todos, { includeCompleted })` — FR-13, FR-15, FR-17.
  Returns `{ Q1, Q2, Q3, Q4, unsorted }`, each a sorted array. Counts come
  from the array lengths.

## 4. Data layer

### 4.1 Interface

```ts
export interface TodoRepository {
  getAll(): Promise<Todo[]>;
  get(id: string): Promise<Todo | undefined>;
  put(todo: Todo): Promise<void>; // insert or replace; rejects InvalidTodoError
  delete(id: string): Promise<void>; // unknown id is a no-op
  subscribe(observer: TodoObserver): () => void; // see below
}

interface TodoObserver {
  next(todos: readonly Todo[]): void; // full list on subscribe and after each change
  error?(error: unknown): void;
}
```

`subscribe` sends the full list, rather than only saying "something
changed", so the State layer can keep that list as its snapshot without
reading storage again. The complete contract is written in the doc comment
in `src/data/TodoRepository.ts`, and `TodoRepository.contract.ts` tests it.

The interface is small on purpose. With at most about 1,000 todos (NFR-4),
the app loads all of them and filters them in memory. This keeps querying
simple and makes it easy to write a fake repository for tests.

### 4.2 Dexie implementation

```ts
db.version(1).stores({ todos: 'id, createdAt' });
```

- **Booleans and `null` cannot be IndexedDB keys.** For this reason
  `isCompleted` and `quadrant` are not indexed. Filtering happens in memory
  (see 4.1).
- `subscribe` uses Dexie's `liveQuery`. Listeners are notified of changes
  made in this tab and, through Dexie's built-in broadcast, in other tabs.
- Each `put` or `delete` is a single IndexedDB transaction, so it either
  succeeds completely or not at all (NFR-5).
- **Data checks on load and on write:** each stored record is checked against
  a Zod schema (`todoSchema.ts`) when it is loaded. A record that fails the
  check is skipped and reported through `onInvalidRecord` (by default
  `console.warn`), so one bad record cannot crash the app. `put` checks too,
  and rejects a malformed todo before anything is written.
- The schema checks only the **shape** of a record, including the completion
  invariant. It does not check the domain's length limits, so data saved under
  older rules still loads. Unknown extra fields are removed, not rejected.
- **Tests:** they use `fake-indexeddb`. It is installed globally in
  `src/test/setup.ts`, because Dexie's `liveQuery` needs the global IDB
  classes when it loads. Each test also passes its own `new IDBFactory()` so
  tests never share data.
- **Schema changes (during development):** fields are expected to change, so
  there are no migrations yet. Edit `version(1)` in place, or bump the version
  with no upgrade code, and clear local data if needed. Before a real release,
  switch to adding a `db.version(n).upgrade()` step with a test for each change.

### 4.3 In-memory implementation

The in-memory implementation is backed by a `Map`. Component tests use it.
Both implementations pass the same shared **contract test suite**, so they
are known to behave the same way. The Dexie tests run on `fake-indexeddb`.

## 5. State layer

- **`TodoProvider`** (`state/TodoProvider.tsx`) is given a `TodoRepository`
  by whoever renders it: Dexie in `main.tsx`, the only place that picks real
  storage, and in-memory in tests. It creates exactly one `TodoStore` and one
  `TodoService` for the app.
- **`TodoStore`** (`state/TodoStore.ts`) is the **only** subscriber to
  `repo.subscribe` in each tab. It holds `{ status, todos, loadError,
saveError }`, where `status` is `loading`, `ready`, or `error`.
  - Its `subscribe`/`getSnapshot` pair is shaped for `useSyncExternalStore`.
  - The snapshot object only changes when the state changes.
  - The storage subscription starts with the first listener and stays open
    while views mount and unmount, so switching views never shows "loading"
    again.
  - `stop()` closes it, and the next listener restarts it. This supports
    React StrictMode's mount, cleanup, mount cycle.
  - If storage fails, the status becomes `error` and the last list that loaded
    is kept. The store then tries again after `retryDelayMs` (default 2 s).
- **`TodoService`** (`state/TodoService.ts`) holds the use cases: `create`,
  `update`, `complete`, `reopen`, `assignQuadrant`, `remove`.
  - Each one reads the todo, applies a domain rule, and saves the result. When
    the rule returns the same object (nothing changed), the save is skipped.
  - The clock and id generator are passed in (`lib/clock.ts`).
  - Methods never throw. They return a `Result` with an error `kind` of
    `validation`, `notFound`, or `storage`. Storage failures are also
    reported to the store (`saveError`).
- **`useTodos()`** returns the store state. It uses `useSyncExternalStore` on
  the shared store, so the list and the matrix always show the same data
  (FR-16). No Redux or Zustand is needed.
- **`useTodoActions()`** returns the service methods plus `pending`, which is
  true while an action started from that component is running.
- **`ErrorBanner`** (`ui/components`, shown in the app shell) uses
  `role="alert"`.
  - While `status` is `error`, it explains that storage can't be reached, for
    example in private browsing. It clears once storage recovers.
  - A failed save shows "couldn't be saved" until the user dismisses it.
- **Known limitation:** each action reads, changes, then writes the todo, with
  no transaction around the whole step. Two changes to the same todo at the
  same moment, such as in two tabs, are resolved by "last write wins". That's
  acceptable for a single user.

## 6. UI layer

### 6.1 Routing (TanStack Router)

The app uses **TanStack Router** with **file-based routing**. The
`@tanstack/router-plugin` Vite plugin scans the `src/routes/` folder and
generates the route tree in `src/routeTree.gen.ts`. That file is generated,
so it is not edited by hand, linted, or formatted, but it is committed so
type-checking works on a fresh clone.

```
src/routes/
├── __root.tsx     app shell: header, tab bar (<Link>), ErrorBanner, <Outlet/>
├── index.tsx      "/"        → ListView
└── matrix.tsx     "/matrix"  → MatrixView
```

**The status filter lives in the URL, and its type is checked.** The `/`
route checks its search parameters with a Zod schema:

```ts
const listSearch = z.object({
  status: z.enum(['all', 'active', 'completed']).default('active').catch('active'),
});

export const Route = createFileRoute('/')({
  validateSearch: listSearch,
  search: { middlewares: [stripSearchParams({ status: 'active' })] },
  component: ListView,
});
```

- `Route.useSearch()` returns `{ status: 'all' | 'active' | 'completed' }`,
  so components never handle the raw text from the URL.
- The default is `active` (FR-9). A missing or invalid value such as
  `?status=bogus` is treated as `active`.
- `stripSearchParams` keeps the default out of the URL, so the Active
  filter is just `/` and other filters look like `/?status=completed`.
- Changing the filter uses `<Link search={{ status }}>` or
  `navigate({ search })`. The compiler checks both.
- The Matrix view's "show completed" toggle (FR-15) uses the same pattern:
  `/matrix?completed=true`.

**History:** the app uses normal browser history, not hash-style URLs. The
static host must send every address to `index.html` (an SPA fallback). This
is configured when a host is chosen.

**Devtools:** `@tanstack/react-router-devtools` is loaded only in
development.

**Zod** is also used in the data layer to check stored records at runtime
when they are loaded (section 4.2), so the project uses one validation
library throughout.

| Component                       | Purpose                                                                                              | Requirements     |
| ------------------------------- | ---------------------------------------------------------------------------------------------------- | ---------------- |
| `TodoForm`                      | Add/edit dialog with title, description, and quadrant. Shows validation messages next to the fields. | FR-1, FR-2, FR-4 |
| `TodoItem`                      | A row with a checkbox, title, dates, a quadrant badge, and edit/delete buttons.                      | FR-5–8           |
| `ConfirmDialog`                 | Confirms deletion. Uses an accessible `<dialog>`.                                                    | FR-3, Q7         |
| `FilterTabs`                    | All / Active / Completed.                                                                            | FR-9             |
| `QuadrantGrid` / `QuadrantCell` | The 2×2 grid with axis labels and counts.                                                            | FR-12, FR-17     |
| `UnsortedTray`                  | Shows todos with no quadrant. It is also a drop target.                                              | FR-13            |
| `DraggableTodoCard`             | A dnd-kit draggable card.                                                                            | FR-14            |
| `QuadrantPicker`                | A "Move" button on every card. It shows the other quadrants only while open (see §6.6).              | FR-14, NFR-2     |

**Implementation notes (M4):**

- **Native `<dialog>`:** the `Dialog` component uses the native `<dialog>`
  element, so focus trapping, Escape to close, and returning focus come from
  the browser. React's `autoFocus` runs before the dialog is open, so it does
  nothing here. Instead, the element marked `data-autofocus` is focused right
  after `showModal()`. jsdom has no `showModal`, so `src/test/setup.ts`
  includes a minimal polyfill. The real dialog behavior is covered by e2e
  tests.
- **`ListView` reads its search params** with `getRouteApi('/')`, so the
  component doesn't import its own route file. Importing it would create an
  import cycle and break code splitting.
- **The completion checkbox is optimistic.** It shows the new state right away
  and is undone if the save fails. Without this, the controlled checkbox
  snaps back until storage confirms the change. The optimistic value is keyed
  on `updatedAt`, because storage sends fresh copies of every todo after any
  change.
- **Screen reader announcements:** adding, saving, completing, and deleting a
  todo are announced through a `role="status"` region. After a delete, focus
  moves to the page heading.
- **Class names** are joined with `lib/cx.ts`. Lookups in a CSS module are
  typed `string | undefined` because `noUncheckedIndexedAccess` is on.
- **Lint exception for tests:** the boundary rule that stops UI code from
  importing `src/data` doesn't apply to `*.test.*` files. Tests need to set up
  in-memory storage.

### 6.3 Drag-and-drop

The app uses `@dnd-kit/core` 6 (stable). The newer `@dnd-kit/react` is still
pre-1.0. Everything specific to drag-and-drop is in `ui/matrix/dnd.ts`.

- **Drop targets:** there are five, with dnd-kit ids `Q1`–`Q4` and
  `unsorted`. Draggables use the todo's `id`. `quadrantForTarget` maps a
  target id back to a quadrant, or `null` for Unsorted.
- **Sensors:**
  - **Mouse and pen (`CardPointerSensor`):** pressing anywhere on a card and
    moving at least 6 px starts a drag.
  - **Touch (`CardTouchSensor`):** a 250 ms long press starts a drag, so a
    swipe still scrolls the page.
  - **Keyboard (`KeyboardSensor`):** only the card's drag handle responds.
  - Both custom sensors ignore presses that start on the card's own controls
    (checkbox, "Move to" menu, buttons). The handle is the exception; see
    `startsDrag`.
- **Keyboard movement (`jumpBetweenTargets`):** the arrow keys jump straight
  to the nearest target in that direction. dnd-kit's default moves the card a
  few pixels per key press. This works in both the 2×2 grid and the stacked
  phone layout.
  - The start position comes from `currentCoordinates`, not `context.over`.
    `over` only updates after a re-render, so it is stale when keys are
    pressed quickly.
- **Collision detection:** the target under the pointer wins (`pointerWithin`).
  With the keyboard there is no pointer, so it falls back to `rectIntersection`.
- **Drag preview:** a `DragOverlay` shows a copy of the card that follows the
  pointer. The original card is dimmed in place. There is no drop animation.
- **Optimistic moves:** `useOptimisticMoves` shows the card in its new
  quadrant right away, and puts it back if the save fails. It uses the same
  `updatedAt` keying as the checkbox. `onDragEnd` calls `moveTo` through
  `useTodoInteractions`.
- **Screen readers:** announcements use todo titles and quadrant names, for
  example "“Pay rent” is over Schedule." and "“Pay rent” moved to Schedule.".
  The instructions explain the keys and mention the "Move to" menu.
- **Moving without dragging:** every card has a "Move" button (`QuadrantPicker`).
  It uses the disclosure pattern: Escape closes it, and focus returns to the
  button. Its choices are rendered only while it is open. An earlier version
  used a `<select>` on every card, which was slow to render (§6.6).
- **No reordering:** cards cannot be reordered within a quadrant (Q6).
- **Known limitation:** dnd-kit decides the drop target after a re-render.
  Releasing at the exact instant the pointer reaches a target can drop the
  card on the previous one. People see the highlight before letting go, so
  this doesn't happen in practice. The e2e tests wait for the "is over …"
  announcement before releasing, for the same reason.

**Shared view logic:** `ui/components/useTodoInteractions.tsx` holds the
add/edit dialog, the delete confirmation, toggling, moving, and the
`role="status"` announcements. Both views use it. `useOptimisticToggle` is
shared by `TodoItem` (list) and `TodoCard` (matrix).

### 6.4 Styling and responsiveness

The app uses CSS Modules and adds no styling library.

- **Theme:** colors and spacing are CSS custom properties in `ui/global.css`.
  Dark mode follows `prefers-color-scheme`.
- **Quadrants aren't color-only:** each one is named in text and also says
  whether it is urgent and important. Color is only a hint (NFR-2).
- **Layout by screen width:**
  - **960 px and wider:** the Unsorted tray (18 rem) sits beside the matrix.
  - **Narrower than 960 px:** the tray moves above the matrix.
  - **Narrower than 640 px:** the quadrants stack in one column, Q1 to Q4,
    without axis labels (NFR-3).

### 6.5 Accessibility and polish (M6)

- **Skip link:** "Skip to main content" is the first Tab stop. It moves focus
  to `<main>` directly rather than using a `#main` URL, so the router's URL
  stays clean.
- **Page titles:** each route sets its own title through its `head` option, and
  `<HeadContent />` renders it from the app shell. React 19 hoists `<title>`
  into `<head>`. `index.html` has no `<title>` of its own, which avoids a
  duplicate.
- **Filter tabs:** they use `activeOptions={{ exact: true }}`. TanStack's
  `<Link>` matches search params partially by default. Without this, the
  Active link (`/`) also counted as active on `/?status=all`.
- **Error state:** if storage fails before anything has loaded, both views say
  the todos can't be shown, not "No todos yet". If it fails later, the last
  loaded todos stay visible. In both cases the banner explains the problem.
- **Touch targets:** on touch screens (`pointer: coarse`), small controls such
  as Edit, Delete, the "Move to" menu, the drag handle, and "+ Add" are at
  least 40 px tall.
- **Reduced motion:** when the user asks for reduced motion, transitions and
  animations are turned off.
- **Automated checks:** `e2e/a11y.spec.ts` runs axe with the WCAG 2.0, 2.1,
  and 2.2 A/AA rules. It covers light and dark mode, desktop and phone, both
  views, and the open dialogs, including validation errors.

### 6.6 Performance (M7, NFR-4)

`e2e/nfr4.perf.spec.ts` measures timings inside the page against the
production build, with 1,000 todos (800 active, 200 completed). Run it with
`npm run e2e:perf`. Profiling found three problems, fixed in this order:

| Problem                                                                                                                     | Fix                                                                                                      | View switch (List → Matrix) |
| --------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- | --------------------------- |
| 800 native `<select>` menus, 5 options each, one per card                                                                   | The "Move" menu renders its choices only while open                                                      | 1,024 → 417 ms              |
| 800 draggable cards rendered at once                                                                                        | Each quadrant shows its first 50 cards (`ui/matrix/limits.ts`), then "Show N more" (FR-17a)              | 417 → ~260 ms               |
| Layout (≈100 ms per switch): `1fr` grid columns measured every card's min-content, and cards off screen were still laid out | `minmax(0, 1fr)` columns, and `content-visibility: auto` with `contain-intrinsic-size` on cards and rows | ~260 → 64–149 ms            |

- **`content-visibility: auto` side effect:** it implies paint containment, which
  clipped the open Move menu. `.card:has(.movePanel)` switches it off while the
  menu is open. The e2e tests caught this; the jsdom tests could not.
- **Typical results now** (median of 7, after a warm-up run): interactions take
  about 30–150 ms, and cold loads take about 200–300 ms. The budgets are
  200 ms and 1 s.
- **Noisy timings:** on a laptop, whole runs can be about 2.5× slower when the
  CPU is throttled or busy. The perf config retries a failing test up to twice,
  so a real regression still fails, and a pass on retry is reported as flaky.

## 7. Testing strategy

| Level         | Tool                                                                      | What it covers                                                                                                                                                                               |
| ------------- | ------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Unit          | Vitest                                                                    | All domain rules and selectors, using a fixed clock. This includes edge cases such as titles of 200 vs. 201 characters, titles that are only spaces, completing a todo twice, and reopening. |
| Data contract | Vitest + `fake-indexeddb`                                                 | One suite run against both repository implementations, plus migration tests.                                                                                                                 |
| Component     | Vitest + React Testing Library + `user-event`                             | Forms, filters, picking a quadrant without dragging, and the confirm dialog. Uses the in-memory repository.                                                                                  |
| End-to-end    | Playwright (Chromium, WebKit; Firefox when the VC++ runtime is installed) | `acceptance.spec.ts` (AC-1–AC-5), `list.spec.ts`, `matrix.spec.ts` (mouse/keyboard drag, Move menu, phone layout), `smoke.spec.ts` (titles, skip link, storage).                             |
| Accessibility | `@axe-core/playwright`                                                    | WCAG 2.x A/AA scans of both views and dialogs, light/dark, desktop/phone (NFR-2). Added in M6 (§6.5).                                                                                        |
| Performance   | Playwright, own config                                                    | `nfr4.perf.spec.ts`, run with `npm run e2e:perf`: production build, 1,000 todos, interactions under 200 ms and cold loads under 1 s (§6.6).                                                  |

**Coverage target:** 100% of the domain layer and at least 80% overall.

## 8. Tooling

- Node 26 LTS (see `.nvmrc`), npm.
- TypeScript 6.0 in `strict` mode, with `noUncheckedIndexedAccess` turned on.
  TypeScript 7 can't be used yet because typescript-eslint supports only
  versions below 6.1.
- ESLint 10 with typed linting (typescript-eslint `strictTypeChecked`), plus
  react-hooks, jsx-a11y, and Prettier. jsx-a11y doesn't officially list ESLint 10
  as supported yet. It is installed through an npm `overrides` entry, and its
  rules have been checked to work.
- `eslint-plugin-playwright`, applied only to `e2e/**`, using its
  `recommended` config. This catches common Playwright mistakes, such as a
  missing `await` on an assertion (`missing-playwright-await`), `page.waitForTimeout`
  (`no-wait-for-timeout`), a `test.only` left in by accident (`no-focused-test`),
  and preferring web-first assertions (`prefer-web-first-assertions`).
- `@tanstack/eslint-plugin-router`, using its `recommended` config. It
  enforces the property order in route options that TanStack Router needs
  for type inference.
- `src/routeTree.gen.ts` is excluded from ESLint and Prettier.
- An import-boundary rule that stops `src/ui/**` and `src/routes/**` from
  importing `src/data/**`. This enforces the layering in section 1.
- npm scripts: `dev`, `build`, `preview`, `test`, `test:watch`,
  `test:coverage`, `e2e`, `lint`, `typecheck`.
