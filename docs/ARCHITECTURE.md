# ToDoPrioritizer — Architecture Plan (Draft v0.1)

Status: **v0.2 — all decisions made; ready for M0**
Implements: `docs/REQUIREMENTS.md` v0.3

## 1. Overview

The app is a single-page React application with no backend. The code is
split into four layers. Each layer may only use the layers below it.

```
┌──────────────────────────────────────────────┐
│ UI         React components and views        │  src/ui/
├──────────────────────────────────────────────┤
│ State      hooks + TodoService (use cases)   │  src/state/
├──────────────────────────────────────────────┤
│ Domain     types, rules, selectors (pure TS) │  src/domain/
├──────────────────────────────────────────────┤
│ Data       TodoRepository + implementations  │  src/data/
└──────────────────────────────────────────────┘
```

- **Domain** contains plain TypeScript only. It does not use React, Dexie, or
  the browser, and it has no side effects. All business rules live here.
- **Data** knows how todos are stored. Its interface is the only place that
  would change if a backend were added.
- **State** connects the domain rules to the repository and gives components
  reactive data through hooks.
- **UI** shows the data and turns user actions into calls to the State layer.
  UI code never imports `src/data/` directly.

## 3. Domain layer

### 3.1 Types

The rule "`completedAt` is set if and only if the todo is done" is built into
the type, so the compiler rejects any todo that breaks it:

```ts
export type Quadrant = 'Q1' | 'Q2' | 'Q3' | 'Q4';
export type IsoUtc = string; // e.g. "2026-11-20T22:15:00.000Z"

interface TodoBase {
  id: string; // crypto.randomUUID()
  title: string; // 1–200 characters, trimmed
  description: string; // 0–2000 characters, '' if none
  quadrant: Quadrant | null; // null = Unsorted
  createdAt: IsoUtc;
  updatedAt: IsoUtc;
}
export interface ActiveTodo extends TodoBase {
  isCompleted: false;
  completedAt: null;
}
export interface CompletedTodo extends TodoBase {
  isCompleted: true;
  completedAt: IsoUtc;
}
export type Todo = ActiveTodo | CompletedTodo;
```

Timestamps are ISO-8601 UTC strings. They can be sorted as plain text, are
easy to read in DevTools, and are converted to local time only when shown
(`lib/formatDate.ts`, which uses `Intl.DateTimeFormat`).

### 3.2 Rules (`todo.rules.ts`)

These functions are pure: they never change their input and always return a
new todo. The current time and new ids are passed in as arguments, so tests
can control them.

| Function                               | Requirement | Behavior                                                                                                    |
| -------------------------------------- | ----------- | ----------------------------------------------------------------------------------------------------------- |
| `validateTodoInput(input)`             | FR-4        | Returns `Result<ValidInput, ValidationError[]>`. Trims the title and rejects one that is blank or too long. |
| `createTodo(input, now, id)`           | FR-1        | Returns an `ActiveTodo` and sets `createdAt = updatedAt = now`.                                             |
| `editTodo(todo, patch, now)`           | FR-2        | Changes the title, description, and quadrant. Keeps `createdAt`, `completedAt`, and the completion state.   |
| `completeTodo(todo, now)`              | FR-5        | Returns a `CompletedTodo`. Does nothing if the todo is already done.                                        |
| `reopenTodo(todo, now)`                | FR-6        | Returns an `ActiveTodo` with `completedAt = null`.                                                          |
| `assignQuadrant(todo, q \| null, now)` | FR-14       | Sets the quadrant. Null moves the todo to Unsorted.                                                         |

Every change also sets `updatedAt = now`.

### 3.3 Selectors (`selectors.ts`)

- `filterByStatus(todos, 'all' | 'active' | 'completed')` — FR-9
- `sortForList(todos, filter)` — FR-10. Newest `createdAt` first. The
  Completed filter sorts by `completedAt`, newest first.
- `groupByQuadrant(todos, { includeCompleted })` — FR-13, FR-15, FR-17.
  Returns `{ Q1, Q2, Q3, Q4, unsorted }`, each a sorted array. Counts come
  from the array lengths.

## 4. Data layer

### 4.1 Interface

```ts
export interface TodoRepository {
  getAll(): Promise<Todo[]>;
  put(todo: Todo): Promise<void>; // insert or replace
  delete(id: string): Promise<void>;
  subscribe(listener: () => void): () => void; // fires after any change
}
```

The interface is small on purpose. With at most about 1,000 todos (NFR-4),
the app loads all of them and filters them in memory. This keeps querying
simple and makes it easy to write a fake repository for tests.

### 4.2 Dexie implementation

```ts
db.version(1).stores({ todos: 'id, createdAt' });
```

- **Booleans and `null` cannot be IndexedDB keys.** For this reason
  `isCompleted` and `quadrant` are not indexed. Filtering happens in memory
  (see 4.1).
- `subscribe` uses Dexie's `liveQuery`. Listeners are notified of changes
  made in this tab and, through Dexie's built-in broadcast, in other tabs.
- Each `put` or `delete` is a single IndexedDB transaction, so it either
  succeeds completely or not at all (NFR-5).
- **Data checks on load:** each stored record is checked against a Zod
  schema when it is loaded. A record that fails the check is skipped and
  logged, so one bad record cannot crash the app.
- **Schema changes:** any change bumps `db.version(n)` and adds an
  `.upgrade()` step. Each migration gets a test.

### 4.3 In-memory implementation

The in-memory implementation is backed by a `Map`. Component tests use it.
Both implementations pass the same shared **contract test suite**, so they
are known to behave the same way. The Dexie tests run on `fake-indexeddb`.

## 5. State layer

- **`RepositoryContext`** gives the app its `TodoRepository`. In production
  this is the Dexie implementation; in tests it is the in-memory one.
- **`TodoService`** holds the use cases. Each one reads the todo, applies a
  domain rule, then saves it, for example:
  `complete(id) → repo.put(completeTodo(todo, clock.now()))`.
  The clock and id generator are passed in so tests can control them.
- **`useTodos()`** uses `useSyncExternalStore` on `repo.subscribe`, so the
  list and the matrix always show the same data (FR-16). No separate store,
  such as Redux or Zustand, is needed.
- **`useTodoActions()`** gives components the service methods. It also
  tracks whether a save is in progress and whether it failed.
- **Error handling:** if a save fails, `ErrorBanner` shows a message that
  does not close by itself. If IndexedDB cannot be opened at all (for example,
  in some private browsing modes), the app shows a page explaining that it
  cannot save data.

## 6. UI layer

### 6.1 Routing (TanStack Router)

The app uses **TanStack Router** with **file-based routing**. The
`@tanstack/router-plugin` Vite plugin scans the `src/routes/` folder and
generates the route tree in `src/routeTree.gen.ts`. That file is generated,
so it is not edited by hand, linted, or formatted, but it is committed so
type-checking works on a fresh clone.

```
src/routes/
├── __root.tsx     app shell: header, tab bar (<Link>), ErrorBanner, <Outlet/>
├── index.tsx      "/"        → ListView
└── matrix.tsx     "/matrix"  → MatrixView
```

**The status filter lives in the URL, and its type is checked.** The `/`
route checks its search parameters with a Zod schema:

```ts
const listSearch = z.object({
  status: z.enum(['all', 'active', 'completed']).default('active').catch('active'),
});

export const Route = createFileRoute('/')({
  validateSearch: listSearch,
  search: { middlewares: [stripSearchParams({ status: 'active' })] },
  component: ListView,
});
```

- `Route.useSearch()` returns `{ status: 'all' | 'active' | 'completed' }`,
  so components never handle the raw text from the URL.
- The default is `active` (FR-9). A missing or invalid value such as
  `?status=bogus` is treated as `active`.
- `stripSearchParams` keeps the default out of the URL, so the Active
  filter is just `/` and other filters look like `/?status=completed`.
- Changing the filter uses `<Link search={{ status }}>` or
  `navigate({ search })`. The compiler checks both.
- The Matrix view's "show completed" toggle (FR-15) uses the same pattern:
  `/matrix?completed=true`.

**History:** the app uses normal browser history, not hash-style URLs. The
static host must send every address to `index.html` (an SPA fallback). This
is configured when a host is chosen.

**Devtools:** `@tanstack/react-router-devtools` is loaded only in
development.

**Zod** is also used in the data layer to check stored records at runtime
when they are loaded (section 4.2), so the project uses one validation
library throughout.

### 6.3 Drag-and-drop

dnd-kit is set up with a `DndContext` that uses `PointerSensor`,
`TouchSensor`, and `KeyboardSensor`. There are five drop targets: Q1–Q4 and
Unsorted. `onDragEnd` calls `service.assignQuadrant(id, target)`. Screen
reader announcements are customized to use the quadrant names ("Moved 'Pay
rent' to Do Now"). Cards cannot be reordered within a quadrant (Q6).

### 6.4 Styling and responsiveness

The app uses CSS Modules and adds no styling library. Colors and spacing are
defined as CSS custom properties. Each quadrant is identified by its text
label and an icon as well as its color (NFR-2). Screens narrower than 640px
show the four quadrants stacked in one column, Q1 to Q4 (NFR-3).

## 7. Testing strategy

| Level         | Tool                                          | What it covers                                                                                                                                                                               |
| ------------- | --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Unit          | Vitest                                        | All domain rules and selectors, using a fixed clock. This includes edge cases such as titles of 200 vs. 201 characters, titles that are only spaces, completing a todo twice, and reopening. |
| Data contract | Vitest + `fake-indexeddb`                     | One suite run against both repository implementations, plus migration tests.                                                                                                                 |
| Component     | Vitest + React Testing Library + `user-event` | Forms, filters, picking a quadrant without dragging, and the confirm dialog. Uses the in-memory repository.                                                                                  |
| End-to-end    | Playwright (Chromium, Firefox, WebKit)        | AC-1 to AC-5, keeping data across reloads, keyboard drag-and-drop, and a mobile-size screen.                                                                                                 |
| Accessibility | `@axe-core/playwright`                        | Automated checks of both views (NFR-2).                                                                                                                                                      |
| Performance   | Playwright                                    | A test that loads 1,000 todos and checks that each view renders in under 200 ms (NFR-4).                                                                                                     |

**Coverage target:** 100% of the domain layer and at least 80% overall.

## 8. Tooling

- Node 26 LTS (see `.nvmrc`), npm.
- TypeScript 6.0 in `strict` mode, with `noUncheckedIndexedAccess` turned on.
  TypeScript 7 can't be used yet because typescript-eslint supports only
  versions below 6.1.
- ESLint 10 with typed linting (typescript-eslint `strictTypeChecked`), plus
  react-hooks, jsx-a11y, and Prettier. jsx-a11y doesn't officially list ESLint 10
  as supported yet. It is installed through an npm `overrides` entry, and its
  rules have been checked to work.
- `eslint-plugin-playwright`, applied only to `e2e/**`, using its
  `recommended` config. This catches common Playwright mistakes, such as a
  missing `await` on an assertion (`missing-playwright-await`), `page.waitForTimeout`
  (`no-wait-for-timeout`), a `test.only` left in by accident (`no-focused-test`),
  and preferring web-first assertions (`prefer-web-first-assertions`).
- `@tanstack/eslint-plugin-router`, using its `recommended` config. It
  enforces the property order in route options that TanStack Router needs
  for type inference.
- `src/routeTree.gen.ts` is excluded from ESLint and Prettier.
- An import-boundary rule that stops `src/ui/**` and `src/routes/**` from
  importing `src/data/**`. This enforces the layering in section 1.
- npm scripts: `dev`, `build`, `preview`, `test`, `test:watch`,
  `test:coverage`, `e2e`, `lint`, `typecheck`.
